# 官方 EmbeddingRWKV 与本地搜索对照（2026-10-28）

本报告区分三件事：模型推理是否算对、量化是否改变排序、应用是否丢掉已有的候选。不能用“官方也有搜不到的词”直接证明本项目没有代码问题。

## 固定来源与范围

- 官方仓库：<https://github.com/howard-hou/EmbeddingRWKV>，版本 `3c306736c58550f4be6d384be068512ba9bfbd72`。使用新克隆的原始 `rwkv-emb.c/rwkv_emb.c`，没有修改计算源码。
- 模型：官方 Tiny `rwkv0b1-emb-curriculum.pth`，768 维、12 层、RETR head。检查点 SHA-256 为 `9033eec92f163d1a710474977fa3fb68b7ee04697e0e961d83434743bd256a15`；已与 Hugging Face 官方文件的 LFS SHA-256 核对一致。
- 官方 C 权重中的全部 410 个张量逐一与检查点比较，值完全一致。C 源码 SHA-256 为 `50ef7f733b35ec6fb4fbdeab14b8aba3361db50ebf54e615cea117ec9516a3a1`。
- CPU：Intel i7-13700H。官方 C 使用本机 LLVM Clang 编译，FP32，无量化。完整构建身份与原始结果保存在 `.codex-tmp/official-rwkv-20261028/`。
- 固定真实索引快照：14 份文档、6,049 个正文语义窗口；保留小说的全部 5,567 个窗口。没有删除小说或减少候选数。
- 97 条固定查询：68 条正例、9 条控制查询、12 条无直接答案负例、8 条歧义查询。它们是既有开发回归集，已参与此前检索调整，不是客户独立盲测集。
- 应用对照引用 2026-10-27 `run6/result.json` 的冻结结果。已核对根目录 release 核心 SHA-256 仍为 `4285f6651406122e80b194bdf61f5c027d5677d4d68e014d0278db025c3ea6f3`，模型仍为 `b2cfe70957dcabd96c85ab8d4c4928060fd060d74420b562b30889a8f818bead`。

本次仅新增诊断脚本和报告；没有调整搜索实现、同义词规则、阈值、模型、用户文档或用户索引。

## 对照方法

1. **官方 CPU FP32 原始检索**：官方 C 推理，使用与生产相同的文本、分词、单个 EOS、RETR 输出头，再进行余弦相似度排序。
2. **当前 INT8 存量索引的原始检索**：当前模型逐条生成查询向量，直接检索冻结的已有正文向量，去掉应用的支持检查与过滤。
3. **当前 INT8 全量重算的原始检索**：相同窗口重新编码，区分当前量化与存量索引/批次差异。
4. **当前应用最终结果**：包含结构锚点、关键词回退、通用确认查询、支持条件、门槛与去重。它与前三项的检索算法不同。

前三项的文档分数为该文档所有窗口中的最高余弦相似度，所有文档都保留，不设无答案阈值。不能把“总能返回一个结果”算作召回质量，也不能把它和应用空结果率直接比较。

每份文档窗口输入为文件名前 160 字符、换行及现有窗口正文。正文窗口通常为约 480 字符。本轮最长窗口输入为 495 token，最长查询为 23 token，全部低于 1,024 token 上限，未发生截断。

同时统计预先标注原句所在窗口在全体 6,049 个窗口中的排名。原句只标注了某一种相关表达，不穷尽所有相关段落，特别是“赔偿”“心率”等短原句。因此该指标是证据定位诊断，不能称为完整片段准确率。

## 推理数值验证

- 从干净官方源码提取独立 PyTorch FP32 递推和模型定义，验证 16、64、256 token，逐层核对 12 层及输出；最终归一化向量最大绝对误差小于 `9e-7`。
- 54 条中文、英文、Unicode、空文本、长文本，以及各文件首/中/末窗口，核对官方 C 与本项目 FP32 ONNX/Rust WKV 路径；最小向量余弦为 `0.999999046`，最大绝对误差约 `3.76e-6`。
- 另外核对串行与 OpenMP C 构建，在 12 条实际窗口上的输出相同。两种构建用于避开 PyTorch 与 LLVM OpenMP 运行库冲突，没有设置忽略冲突的环境变量。
- 分词 ID 与本项目 tokenizer 一致；重复推理不保留上次调用的循环状态。

这些结果没有发现当前 FP32 模型导出、矩阵方向、WKV 衰减、状态更新顺序或 RETR 输出头的明显计算错误。验证覆盖本次样本与路径，不等于证明全部应用代码没有问题。

## 全量排名结果

下表使用相同 68 条正例。原始余弦检索不设置阈值；应用最终结果包含过滤和结构/词项信号。

| 路径 | 目标文件第一 | 目标文件前三 | 目标文件前十 | 标注证据窗口第一 | 标注证据窗口前十 |
|---|---:|---:|---:|---:|---:|
| 官方 C FP32、单 EOS、原始余弦 | 61/68 | 68/68 | 68/68 | 31/68 | 58/68 |
| 当前 INT8 查询 + 存量正文向量、原始余弦 | 60/68 | 68/68 | 68/68 | 32/68 | 59/68 |
| 当前 INT8 查询 + 本轮重算全部窗口、原始余弦 | 60/68 | 68/68 | 68/68 | 32/68 | 59/68 |
| 当前应用最终结果 | 60/68 | 62/68 | 62/68 | 不使用此统计口径 | 不使用此统计口径 |

只有 14 份文档时，文件进入前十是很宽松的指标，不能把 `68/68` 宣传为完整搜索准确率。官方原始检索只有 31 条查询把某个预标注证据窗口排第一，说明“找对文件”与“找对细节”仍然有差距。

9 条控制查询中，官方与当前 INT8 原始检索均有 6 条目标文件排第一；应用为 8/9。结构/词项信息并非只有负面作用，例如“排行榜”官方原始文档排第 4，应用排第 1。

官方 FP32 与当前 INT8 存量检索在 68 条正例中有 67 条目标文件排名相同。证据窗口排名有 45 条完全相同，其余发生变化。量化与存量向量差异会影响接近分数下的排序，但本轮主要文件漏召回不能简单归因于 INT8。

本轮重算的 INT8 与存量索引在全部 77 条有目标查询（68 正例 + 9 控制）中文件排名完全相同。存量与重算向量的余弦中位数约为 `1.0`，最低约为 `0.9932`；不同调用批次下的动态量化等因素仍需另外隔离，不能根据个别向量不完全一致就断言缓存损坏或模型版本错误。本轮未重建用户索引。

官方 FP32 与当前 INT8 重算正文向量的余弦中位数约为 `0.99899`，最低约为 `0.99537`；查询向量中位数约为 `0.99835`，最低约为 `0.99401`。这是可测的量化偏差，不是两种 FP32 实现间的计算误差。

### 应用未返回的 6 条正例

“证据排名”在全体 6,049 个正文窗口中计算；应用列指预标注目标文件。

| 查询 | 官方目标文件排名 | 当前 INT8 存量排名 | 官方标注证据排名 | 应用是否返回目标 |
|---|---:|---:|---:|---|
| 送过来的东西坏了谁掏钱 | 2 | 2 | 3769 | 否 |
| 货不对板能不能退回去 | 2 | 2 | 3 | 否 |
| 交货少了应该怎么补 | 1 | 1 | 6 | 否 |
| 出了纠纷去哪个法院 | 1 | 1 | 72 | 否 |

| 自动识别文件类型并提取元数据的工具 | 3 | 3 | 27 | 否 |

这些情况不能统一归类：

- **检索过滤影响明确**：“交货少了”“断网以后”在官方与当前向量原始排名中均有目标文件第一，且标注证据在前十，应用仍未返回。代码中的 `body_is_supported`、通用确认查询相似度、局部词项支持及最终门槛会拒绝候选。见 `crates/search-core/src/search.rs`。这并不自动说明应无条件放宽门槛，因为负例相似度有重叠。
- **模型/表示排序明显不足**：“送过来的东西坏了谁掏钱”在官方 FP32 中更偏向小说的付款/交易场景，标注赔偿段落排第 3769。去掉量化不能解决当前窗口输入下的偏差；短条款实验又显示输入范围能改善分数，所以不能称为模型在所有输入方式下的绝对能力上限。
- **两种因素叠加**：“货不对板”官方证据已经排第 3，但小说的无关“板”等内容仍略高，应用又过滤目标。“出了纠纷”文件排第一，但该文件最相似窗口不等于法院条款，模型定位与过滤均有影响。
- **标注也有限制**：Tika 的中文查询对应英文说明，中文软件需求文件同样包含相关“格式识别/提取”要求。预标注 `testPDF.pdf` 排第 3，不代表前两条在语义上一定完全无关。

控制查询“榜单”官方目标文档排第 9、标注证据排第 77，当前 INT8 存量分别为第 9、第 66；应用不返回。该短词本身也缺少“大学”的约束，不能要求唯一确定大学表格。

### 负例与阈值

原始余弦一定会返回候选，不具备“没有答案”的直接判定能力。例如当前向量对“Linux服务器磁盘扩容操作手册”的最高分约 `0.618`，实际文档只涉及相关设备/搜索需求；“Python虚拟环境依赖冲突排查教程”约 `0.510`。正例目标文档最高分则低至约 `0.249`。正负分数显著重叠，不能靠一个全局阈值同时解决漏召回和误召回。

应用已有 12 条无直接答案负例中仍有 3 条非空，这里引用冻结结果，不把原始余弦返回候选另算为“官方误召回率”。

## 官方输入协议与分段的补充诊断

官方 README 的 Quickstart 使用单 EOS；官方评测实现还支持短文本重复、多 EOS 平均、2048/512 配置。这是两个不同输入协议，不能把后者当成同输入数值验证。

对 11 条查询、49 个固定候选窗口另做小范围对照。候选来自当前 INT8 前五窗口及预标注证据窗口的并集，包含已知正确位置，因此下列结果**不是全量召回率**。

| 查询 | 单 EOS，含文件名：证据排名 | 单 EOS，仅正文：证据排名 | 官方评测多 EOS：证据排名 |
|---|---:|---:|---:|

多 EOS 对部分查询有改善，对另一些查询退步，不能直接认为恢复官方评测预处理就会全面解决问题。仅正文输入也没有统一改善。生产没有应用这些实验变更。

另外在已知原句位置的前提下，将原有约 480 字正文裁成以证据为中心的 96 字，仅用于观察输入范围影响：

- “货不对板能不能退回去”：官方 FP32 相似度从约 `0.319` 变为 `0.519`。
- “送过来的东西坏了谁掏钱”：从约 `0.200` 变为 `0.341`。
- “交货少了应该怎么补”：从约 `0.267` 变为 `0.244`。

这说明上下文混合会影响表示，短窗口也不是越短越好。这种利用答案位置的裁剪不能作为可部署算法或准确率提升结果，更不证明已达到模型能力的最终上限。

## 结论与建议

本次证据**不支持“不是我们的代码问题，只是模型能力边界”这一整体结论**。

1. 当前 FP32 推理与官方独立实现基本一致，没有发现核心推理计算错误；INT8 对文件排名影响相对小。
2. 应用检索层确实会丢掉已由模型排到前面的目标，应优先改进候选保留、支持检查和展示片段选择，同时保留负例评测，避免只靠降低统一阈值换取召回。
3. 官方未量化模型在当前文本窗口输入下也有明显的口语和细节排序不足；分段和上下文混合会进一步影响结果。可继续研究通用条款/段落边界与多粒度证据定位，不需要“赔款→违约金”类领域映射。
4. 官方多 EOS 在部分样本上改善、部分退步，且增加处理量。本次没有足够证据支持直接全量替换现有输入协议。
5. 此次是已有开发回归集的归因实验。后续需用客户未参与调参的真实查询与更多干扰文件盲测，才能评估产品泛化准确率。没有把本轮结果称为模型最终能力上限。

## 复现与原始证据

诊断脚本：`scripts/compare-official-rwkv.py`。默认路径固定到本次快照、官方克隆和模型，避免误读正在运行的用户数据库。

官方代码位于 `.codex-tmp/embeddingrwkv-official-20261028`；官方 C 由本次输出目录下的 `build.cmd` 构建。编译选项为 `-O3 -march=native -ffp-contract=fast`；主推理构建增加 `-fopenmp`，数值参考构建不加 OpenMP。编译器来自 VS 2022 的 LLVM x64 工具链。

```powershell
$env:PYTHONIOENCODING='utf-8'
python -B scripts/compare-official-rwkv.py --phase validate
python -B scripts/compare-official-rwkv.py --phase inspect
python -B scripts/compare-official-rwkv.py --phase encode --threads 14
python -B scripts/compare-official-rwkv.py --phase encode-int8 --threads 6
python -B scripts/compare-official-rwkv.py --phase analyze
python -B scripts/compare-official-rwkv.py --phase protocol
python -B scripts/compare-official-rwkv.py --phase oracle
python -B scripts/compare-official-rwkv.py --phase persisted
```

输出目录 `.codex-tmp/official-rwkv-20261028/` 包含：

- `identity.json`：源码、动态库、模型、输入、快照及应用结果哈希。
- `validation.json`、`persisted-validation.json`：数值、分词与存量向量核对。
- `official-vectors.npz`、`int8-fresh-passages.npz`、`int8-singleton-queries.npz`：全量向量及配置身份。

官方原始 C 未修改；CPU FP32 与本项目 FP32 对照没有使用旧工作区中曾改过的 Python CPU 兼容补丁。此次没有重跑官方 13 项 NanoBEIR，报告不把官方公开指标算作本机测试结果。
