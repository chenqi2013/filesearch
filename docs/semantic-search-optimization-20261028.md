# 语义搜索综合优化与验证（2026-10-28）

本轮在上一轮完整窗口证据修正的基础上，检查查询表示、窗口候选、过滤、混合排序及 CPU 成本。保留经过对照验证的通用修改，没有添加领域同义词表、特定文件例外或按测试查询分支。固定开发集的目标文件命中有所提升，但主题相近而没有答案的误召回仍然明显，不能称为所有语义搜索问题已经解决。

## 最终实现

生产修改限于 `crates/search-core/src/search.rs` 和 `crates/search-core/src/storage.rs`。

1. **增加官方检索指令的查询视角。** 沿用原查询及“关于{查询}的资料”确认查询，再增加 `Instruct: Given a query, retrieve documents that answer the query\nQuery: {query}`。该指令来自官方仓库 `rwkv-emb.c/evaluate_nanobeir.py`，原始版本为 `3c306736c58550f4be6d384be068512ba9bfbd72`。它用于所有查询，没有把“赔款”等词替换成其他词。两个检索视角分别计算并保留自己的相对过滤门槛，避免最终检查时混用。
2. **用跨视角一致性补充正文支持。** 原查询和指令查询必须选出同一领先文档，且分别与其他文档有足够差距；指令查询的同一正文窗口仍须满足已有的绝对分数下限和确认查询下限。单个高分窗口、多个来自同一文档的窗口或两个视角意见不一致，都不能代替这一条件。沿用原有分数常量，没有新增面向具体问题的门槛。
3. **保留两种窗口候选。** 每份候选文档保留原查询高分窗口及原查询／确认查询联合高分窗口的并集，并继续保留相关 BM25 窗口。长文档中，联合支持较强的深层窗口不再仅因为原始分数排在第八名之后而被丢掉。正文所有已存窗口仍参与计算，常规候选每视角至多保留 16 个窗口，另加相关 BM25 窗口；这不是减少持久化全文窗口。
4. **减少候选筛选开销。** 窗口评分阶段不再逐窗口复制文档 ID；先按文档归组，以部分选择保留文档和窗口，只对最后选中的候选排序、复制文本。避免对全文窗口执行完整排序。确认相似度需要覆盖全文窗口，且增加了一个查询视角，不能仅凭这一结构修改宣称整体查询加速。
5. **隔离短词规则的适用范围。** 原有短中文词的字符支持及加分只用于原查询视角，不将其数值判断直接套到新增指令视角。中间版本曾使“结账”的混合结果从合同第一变成小说第一；修正后恢复合同第一。

RWKV Tiny、CPU 推理后端、文档输入协议、全文向量生成、索引格式均不变。现有索引可以直接使用，不需要重建；索引阶段没有新增文档 embedding。每个有正文向量的语义／混合查询增加一次短查询 embedding，并增加一轮窗口检索。

## 测试范围与结果

所有检索使用同一个原始索引的副本：14 份文档、6,049 个正文窗口、44 个结构锚点，小说的全部 5,567 个窗口保留。前后使用相同文档、向量、查询及目标标注。原始数据库以及副本的文档、向量、锚点和持久向量缓存指纹均保持一致。

三套查询分别为：

- 原有 97 条开发回归查询：68 条正例、9 条控制、12 条无直接答案负例、8 条歧义查询。
- 本轮修改前新增并冻结的补充集：30 条正例、16 条较难负例，文件为 `scripts/fixtures/semantic-holdout-20261028.json`。

这些是开发者编写的查询，补充集也使用同一批文档；不是客户盲测，也不是独立文档库上的通用准确率评估。只有 14 份文档时，前十命中尤其宽松。

## CPU 耗时与取舍

相同 97 条查询的语义接口中位耗时约 **45.9 ms → 66.3 ms**，P95 约 **81.7 ms → 111.1 ms**。补充集语义中位耗时约 **46.2 ms → 75.5 ms**。这些是本机开发样本的接口计时，受 CPU 负载、查询顺序、缓存及文档数量影响，不是客户端耗时保证。

同一查询在三种模式下轮换执行，查询向量会被缓存；因此混合模式约 32–34 ms 的中位数不能解释为一次全冷查询的成本。旧查询对照也观察到语义查询增加数十毫秒。本轮选择以这部分查询成本换取稳定的召回收益，未增加长 TXT 的索引 embedding 工作量。

## 检查过但未采用的方案

- **修改词项的零权重处理。** 给索引中没有出现的词赋正 IDF 后，部分口语查询的原有命中丢失，未观察到稳定净收益。`text_index.rs` 已恢复成本轮修改前的版本。
- **优先展示通过支持判定的窗口。** 补充集的“产品降价没告诉我能追回以前的差价吗”从价格追溯条款变成质量退货条款，指定原句展示量从 21 降到 20，因此撤回该展示策略。
- **官方 RWKV reranker 的 CPU 适配实验。** 检查 idx1610 和完整头权重。在实验适配实现中，24 个候选的完整 FP32 重排约需 13–25 秒，且没有稳定解决关键漏召回；不能直接作为本轮默认检索方案。状态输出适配的 C 推理与原 C 推理在两条文本上的 embedding 最大差为 0，但完整重排头尚未与官方 PyTorch WKV 执行逐值对齐，因此这些结果仅用于探索，不能视为官方 reranker 性能或能力定论。

保留诊断脚本 `scripts/evaluate-rwkv-reranker.py`，没有将其或重排权重接入桌面运行路径。它依赖本地官方源码、已有模型转换文件、PyTorch、NumPy、Visual Studio/Clang，默认使用 `.codex-tmp` 下的本轮实验资源，不是可直接分发的用户功能。可用 `--windows 8 --query-limit 1` 检查一条查询的 24 个候选；结果记录权重、源码适配哈希及候选策略，不使用预标注目标选择候选。

实验权重 SHA-256：idx1610 为 `43ddf1e93acb7c3c907e3d255cfea357f3ca81001a29241892d0b275078f52c9`，完整头为 `6b6f36543ad71aa48bca3cca97863c529e9153515fb777184c36475b3badb6be`。此前保存的六条完整头结果在 `.codex-tmp/rwkv-reranker-20261028/result.json`，属于补充元数据字段之前的脚本输出。
