# 长 TXT CPU Embedding 排查与优化（2026-10-21）

## 范围与结论

应用继续使用现有 EmbeddingRWKV Tiny，不替换模型、不抽样丢弃全文语义窗口。Qwen 和 E5 仅作独立耗时对比，未接入应用。当前实现解决了长文件推理期间状态接口阻塞、缺少窗口进度和中断后重复计算的问题；减少了 TXT 两层切分产生的额外重叠，但不能据窗口数降幅直接宣称同等比例提速。

## 真实文件与瓶颈

- 文件：`小说——超级龙宠.txt`，6,990,767 bytes（约 6.67 MiB），UTF-8。
- SHA-256：`8f66af22bf03e0411f157e8173a5f0fabff5ca9d07c8de63bf590bea547e96d9`。
- 规范化文本：2,226,641 字符。
- 客户截图：读取/解析 116 ms、Embedding 37 分 28 秒、SQLite 995 ms、Tantivy 235 ms。主要瓶颈是模型计算，并非读取 TXT 或数据库写入。
- 旧策略先按 800 字符、步长 700 分段，再对各段按 480/400 切语义窗口；全文产生 6,362 个去重窗口。
- 新策略直接对连续全文按 480/400 切窗口，产生 5,567 个去重窗口（减少 12.5%），保留头、中、尾和分段边界的语义覆盖。新窗口平均更长，因此计算量与时间不会直接减少 12.5%。

16 窗口 ONNX profiler 诊断中，MatMul 约占算子时间 56.1%、WKV7 约 10.8%、DynamicQuantizeMatMul 约 9.4%。这不是端到端耗时分解，但说明只优化 WKV 自定义算子不能解决全部瓶颈。未更改现有权重、量化范围或默认 CPU 线程配置。

## 实现

1. TXT 全文直接切窗，不限窗口数量；其他格式保持原窗口策略。
2. 保留全局相同 Token 长度合批，每批最多四窗口、2,048 Token。小批推理/保存并更新窗口进度，批次之间响应暂停与取消。
3. `/stats` 读取后端信息不再争用推理互斥锁，长文件处理时仍可查询状态。
4. 增加 SQLite 持久向量缓存。相同模型配置和完整输入才可命中；输入包含文件名，避免标题不同而错误复用。只保存真实模型向量，不缓存离线降级向量。
5. 中断后的已完成批次保留，下次索引检查缓存并只计算缺失窗口。未完成文件不写入文档代表向量，避免下次增量扫描误当成完成文件跳过。
6. 文件完成后限制缓存为 100,000 条；768 维 FP32 原始向量约占 293 MiB 上限，另有数据库索引等开销。缓存键不含原文，仅保存 SHA-256 与向量。
7. 保留现有 v9 向量协议，升级不触发所有目录强制重建。已完成的旧索引仍有效；新文件、变化文件和主动重新索引的文件使用新策略。

## 完整小说生产链路实测

独立数据库、全新缓存、完整 6,990,767 bytes 文件，CPU 后端，没有抽样：

| 阶段 | 首次完整索引 | 重启服务、修改副本 mtime 后同内容重建 |
| --- | ---: | ---: |
| 读取/解析 | 36 ms | 39 ms |
| Embedding 阶段 | 1,431.985 秒（23 分 52 秒） | 136 ms（缓存命中，不再推理） |
| SQLite | 7.840 秒 | 2.270 秒 |
| Tantivy | 574 ms | 657 ms |
| 总计记录 | 1,441.164 秒（24 分 1 秒） | 3.102 秒 |
| 含 API 轮询、暂停验证的墙钟时间 | 1,442.519 秒 | 4.341 秒 |

最终数据库为 1 文档、3,181 正文片段、5,567 语义窗口、5,567 条缓存，失败数为 0，无缺失文档代表向量。首次观察到 1,404 次窗口进度变化，暂停后能恢复；首次 `/stats` 最大响应 56.6 ms，缓存重建期间最大响应 260.8 ms。原始数据在 `pipeline-full/result.json` 和 `pipeline-full/service.log`。

全文实测说明：首次全文计算仍要约 24 分钟，并未解决成秒级。136 ms 是复用已有向量时的 Embedding 阶段耗时，不能用于描述首次生成向量的速度；重启后仍需要重新扫描、解析、恢复语义记录和提交关键词索引。

## 对比测试口径

本机为 Intel Core i7-13700H（14 核/20 线程）、约 16 GiB 内存，测试时空闲内存约 2.3 GiB。客户机器和本机不是同一环境，不能用客户截图与本机结果直接计算提速百分比。

以下为同一小说均匀选出的 96 个新策略窗口，文件名前缀相同；向量均验证为有限值且已归一化。仅测推理，模型加载/预热、分词、SQLite 和 Tantivy 另计；不是全文实测，也没有测试准确率高低。

| 测试模型/导出 | CPU 配置 | 96 窗口推理实测 | 按 5,567 窗口线性估算全文 |
| --- | --- | ---: | ---: |
| 现有 RWKV Tiny，后 6 层 FFN INT8、其余 FP32 | 6 线程，相同长度合批，上限 4 | 26.89 秒 | 约 26 分钟 |
| multilingual-e5-small，FP32 ONNX | 6 线程，batch 4 | 7.20 秒 | 约 6 分 57 秒 |
| Qwen3-Embedding-0.6B，INT8 ONNX | 6 线程，batch 1 | 46.73 秒 | 约 45 分 10 秒 |

Qwen/E5 使用本机 Python ONNX Runtime 1.29.0；RWKV 使用项目内置 ONNX Runtime 1.22.0 和 Rust WKV 自定义算子。批次、精度、模型规模、运行时均不同，表格只描述这些具体本地部署配置，不能视为等配置模型排名。E5 使用 `passage: ` 前缀与 masked mean pooling；Qwen 使用最后有效 Token pooling，两者样本均未触及长度上限。

旧策略 RWKV 的另一次 96 窗口采样为 16.59 秒，但旧/新窗口平均 Token 数不同（435.3 / 472.6），且 CPU 调度/温度有明显波动。因此这组采样不能证明首次推理已提速。inter-op 并行和更多线程实验也未表现出稳定收益，默认配置不变。

补充同机、同一 83,734 bytes 副本的交替对照（旧→新→新→旧），全部文本参与纯推理，均为 6 线程、batch 上限 4：旧策略 77 窗口，两次分别 14.19 / 15.97 秒；新策略 67 窗口，两次分别 15.59 / 15.50 秒。新策略平均反而约慢 3.1%，旧策略两次波动超过 12%。因此本轮**没有证据表明首次推理已稳定加速**；直接切窗的确定收益是降低重复窗口数和向量记录数，主要已验证的时间收益来自缓存复用。结果文件为 `rwkv-matched-0.json` 至 `rwkv-matched-3.json`。额外 4 线程测试与编译任务重叠，不用于线程优劣结论。

## 已完成的小样本生产链路验证

从小说均匀抽取 64 段，每段 480 字符，拼成同名的 83,734 bytes 测试副本，独立目录/数据库运行正式 release 搜索服务，不接触用户索引或原文件：

- 首次 Embedding：18.087 秒；总记录 18.154 秒。
- `/stats` 最大响应 22.3 ms，观察到 23 次窗口进度变化。
- 暂停期间窗口数不变，恢复后完成，无索引失败。
- 关闭服务、仅修改测试副本的 mtime、重新启动并索引：Embedding 15 ms，总记录 78 ms；包含客户端轮询的墙钟时间约 0.30 秒。

这验证了缓存复用的收益，不代表全新长小说可以在毫秒内生成向量。

## 后续边界

保留全部正文语义、现有模型和 CPU 执行的前提下，首次计算仍随 Token 总量增长。更激进的全量 INT8、不同推理运行时或跨层融合需要独立的准确率回归和多台客户 CPU 吞吐测试，不在本次直接替换。缓存主要改善重复索引与中断重试；修改文件名或在文本前部插入内容导致窗口输入变化时，仍会有大量缓存未命中。
